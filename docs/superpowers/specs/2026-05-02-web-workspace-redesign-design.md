# Web Workspace 再設計 仕様

作成日: 2026-05-02

## 目的

現在の Web UI は、ユーザーに内部実装の概念をそのまま見せている。

例:

- `workflow_mode`
- `orchestration_mode`
- `source_text`
- `Stream Events`
- エージェント依存関係
- 生ログ

そのため、バックエンドが動いていても、素人には「何を入力すればいいのか」「いま何が起きているのか」がわからない。

再設計後の初回体験は次の流れにする。

1. ユーザーが普通の言葉で依頼を書く。
2. アプリが依頼内容をわかりやすく受け付ける。
3. AI チームが動き出したことが見える。
4. 進行状況が人間にわかる言葉で表示される。
5. 最終回答が読みやすく表示される。
6. あとから解析できる詳細ログも残る。

## 設計原則

最重要視する体験は「自分の指示で何かが動いている」と感じられること。

解析データは残す。ただし、初心者に最初から見せない。生ログ、イベント、エージェント別出力、JSON、差分、file changes は、右側の詳細ペインまたは実行履歴から見られるようにする。

## メイン画面

現在の初期画面 `Execution` を、日常的に使う `Workspace` に置き換える。

Workspace は、現在分散している次の画面の主要機能を統合する。

- Execution
- Team Composer
- QA Gate
- Logs

Workspace は 3 領域で構成する。

1. 左: 依頼
2. 中央: 実行中の作業
3. 右: 詳細解析

## 左: 依頼

左ペインは、素人でもわかる依頼フォームにする。

内部 API 名は表示しない。

最初に見せる入力項目:

- 何をしたいですか？
- 元になる内容を貼ってください
- どんな結果がほしいですか？
- 誰に向けた内容ですか？
- 追加で伝えたいこと

「何をしたいですか？」は、技術用語ではなく用途テンプレートで選ばせる。

テンプレート例:

- 文章をよくしたい
- アイデアを整理したい
- レビューしてほしい
- 実装方法を相談したい
- コードを直したい
- 自由に依頼する

テンプレート選択は、内部的には既存の request に変換する。

- `workflow_mode`
- `objective`
- `global_instruction`
- `source_text`
- `code_context`

ユーザーはこれらのフィールド名を理解する必要がない。

## 中央: 実行中の作業

中央ペインは、ユーザーの依頼で AI チームが動いていることを見せる。

現在の `StreamEvent` は、そのまま表示せず、人間にわかる進行状態へ翻訳する。

表示する進行状態:

- 依頼を受け付けました
- 依頼内容を整理しています
- 作業計画を立てています
- 調査しています
- レビューしています
- 最終回答を作っています
- 完了しました

中央ペインには「ライブメモ」を表示する。

ライブメモは生ログではなく、短く読みやすい説明にする。

例:

- Manager が依頼を 3 つの確認項目に分けました。
- Worker 1 が対象ファイルを確認しています。
- QA が回答内容と依頼内容のズレを確認しています。

最終回答は中央ペインの主役として表示する。差分や file changes はタブや折りたたみで見られるようにする。

## 右: 詳細解析

右ペインは、あとから解析したい人のための領域にする。

表示対象:

- 選択したエージェントの詳細
- エージェント別出力
- 生の stream event
- エラー
- 実行メタデータ
- request / response JSON
- file changes

右ペインは折りたためるようにする。初心者は右ペインを開かなくても実行を完了できる。

## ナビゲーション

サイドバーは「7 画面を順番に回る」印象をやめる。

推奨ナビゲーション:

- Workspace
- Runs
- Teams
- Templates
- Settings

Dashboard、Logs、QA Gate、Execution は、独立した主要画面ではなく、Workspace または Runs の中の補助ビューにする。

## ラベル

メイン画面では、日本語で、行動がわかるラベルを使う。

置き換え例:

- `source_text` -> `元になる内容`
- `objective` -> `ほしい結果`
- `global_instruction` -> `AIチームへの追加指示`
- `workflow_mode` -> `依頼の種類`
- `orchestration_mode` -> 詳細設定に隠す
- `rounds` -> `何回見直すか`, 初期状態では隠す
- `Stream Events` -> `進行状況`
- `Agent Outputs` -> `AIチームの作業内容`
- `Diff Viewer` -> `変更点`

## 実行前チェック

実行ボタンは、実行できる状態かどうかを明確に伝える。

実行開始に必要な条件:

- 依頼の種類が選ばれている
- 依頼内容または元になる内容が入力されている
- 有効なエージェントが 1 人以上いる

足りない場合は、ボタン付近に素直な日本語で表示する。

例:

- 依頼内容を入力してください
- AIチームが選ばれていません
- コード修正では作業フォルダが必要です

## 解析データ

解析機能は残す。

各実行であとから見られるべき情報:

- ユーザーが入力した元の依頼
- 内部的に生成された request payload
- チーム構成
- stream event log
- エージェント別出力
- 最終回答
- 差分
- file changes
- エラー
- 実行時間

最初はフロントエンド state 上で扱い、必要に応じて既存または新規のバックエンド API で永続化する。

## 最初の実装範囲

最初の実装は `app/web` に絞る。

やること:

- Workspace 画面を追加する
- Workspace を初期画面にする
- 技術用語の入力フォームを、初心者向けの依頼フォームに置き換える
- 既存の `startRun`, `stopRun`, `resetRun` を再利用する
- 既存の `StreamEvent` を人間向けの進行ラベルへ変換する
- 生ログは右ペインの詳細解析に移す
- 表の導線から実行ボタンの重複をなくす

やらないこと:

- バックエンドのオーケストレーション変更
- Provider 実行方式の変更
- 完全な実行履歴 DB の新設
- すべての詳細エージェント設定の作り直し
- macOS アプリの再設計

## 確定方針

- 入力は「テンプレート + 自由依頼」にする
- 解析情報は残すが、表の体験では二次情報にする
- Workspace を最初に開く画面にする
- 詳細なエージェント編集は初心者向け導線から外す

## 後で決めること

Teams と Templates を独立画面として残すか、Workspace から開くモーダルにするかは、最初の Workspace 実装後に判断する。
